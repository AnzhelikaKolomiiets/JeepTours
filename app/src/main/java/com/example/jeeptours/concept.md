## 1. Ідея та концепція застосунку 

### 1.1. Контекст та сфера
* **Сфера:** Гірський туризм, офроуд (джипінг) у Карпатах.
* **Основна ідея:** Мобільний застосунок для автоматизованого та автономного розрахунку безпеки гірських маршрутів і вибору відповідного класу позашляховика на основі AI-аналізу умов, рельєфу та ризиків з розрахунком вартості та збереженням у локальну БД.

### 1.2. Brainstorm ідей (5 напрямків)
1. **Масовий продукт:** Туристичний навігатор Карпатами з функцією бронювання стандартних джип-турів (аналог GetYourGuide для Карпат).
2. **Нішевий інструмент (обрано):** AI-оцінювач безпеки та відповідності класу авто для екстремальних гірських маршрутів (Light, Hard, Extreme, VIP).
3. **Gamified:** «Offroad Quest Carpaty» — проходження чекпоінтів на хребтах з нарахуванням балів за безпечний стиль їзди та відкриттям нових локацій.
4. **B2B:** Платформа управління флотом гірських гідів-водіїв, моніторинг зносу авто та диспетчеризація замовлень.
5. **AI + Сенсори:** Мобільний асистент водія, що використовує акселерометр/гіроскоп смартфона для визначення кута нахилу та ризику перекинутися на гірському схилі.

### 1.3. Порівняння з аналогами

| Застосунок / Платформа | Переваги | Недоліки / Обмеження | Чим відрізняється наш проєкт |
| :--- | :--- | :--- | :--- |
| **Wikiloc / Komoot** | Величезна база треків, GPS-навігація, спільнота. | Не враховують підготовку авто (клас, кліренс, лебідку), відсутня оцінка безпеки для проїзду джипом. | Персоналізований розрахунок ризиків залежно від класу авто та складності гірського ділянки. |
| **Локальні чати / Viber-групи** | Прямий контакт з місцевими водіями. | Немає прозорості ціноутворення, суб'єктивна оцінка ризику, відсутність автоматизації. | Автоматизований прозорий розрахунок ризику та миттєва оцінка вартості подорожі. |

### 1.4. Обґрунтування фінального вибору
Обрано **нішевий інструмент з AI-компонентом** (проєкт "Carpathian Offroad AI").
* **Чому для MVP?** Фокус на чіткому POC-сценарії (вибір локації + клас авто $\rightarrow$ AI Safety Verdict + Розрахунок вартості + Збереження в Room DB) дозволяє реалізувати повноцінну Clean Architecture на Android Native (Kotlin + Jetpack Compose) без розпорошення ресурсів.

## 3. Концептуальна архітектура 

Застосунок будується за принципами **Clean Architecture** та **MVVM / MVI** з розділенням на 4 основні шари: **Presentation**, **Domain**, **Data** та **AI / Safety Engine**.

### 3.1. Опис шарів та обґрунтування технологій

* **Presentation Layer:**
    * *Технології:* Kotlin, Jetpack Compose, Material3, StateFlow, ViewModel.
    * *Обґрунтування:* Jetpack Compose забезпечує сучасний декларативний UI, легко інтегрується з реактивними потоками `StateFlow`.
* **Domain Layer:**
    * *Технології:* Pure Kotlin (Coroutines, UseCases, Domain Models).
    * *Обґрунтування:* Незалежний шар бізнес-логіки. Містить `CalculateRouteSafetyUseCase`, `CalculateTripCostUseCase`, `SaveOrderUseCase`.
* **Data Layer:**
    * *Технології:* Room DB (Entity `TripOrder`, DAO `OrderDao`), Flow, Repository Pattern.
    * *Обґрунтування:* Room гарантує надійне локальне збереження замовлень та кешування маршрутів для роботи Offline.
* **AI / Safety Engine Layer:**
    * *Технології:* Rule-Based AI Engine / SafetyEngineEvaluator.
    * *Обґрунтування:* Виконує аналіз відповідності між коефіцієнтом складності маршруту та можливістями обраного класу авто, формуючи показник ризику (Risk Index %) і підсумковий вердикт.

### 3.2. Альтернативи для кожного шару

| Шар | Обраний стек | Альтернативи | Чому відхилено альтернативу |
| :--- | :--- | :--- | :--- |
| **Presentation** | Jetpack Compose | XML Layouts / ViewBinding | Застарілий підхід, більше шаблонного коду (boilerplate). |
| **Data (Local)** | Room DB | Realm / SQLite OpenHelper | Room підтримується Google, чудово працює з Kotlin Coroutines & Flow. |
| **Async / Data Flow** | Kotlin Coroutines & Flow | RxJava3 | Coroutines є нативним рішенням для Kotlin із меншим оверхедом. |

### 3.4. Data Flow для головного сценарію (POC)

1. **User Action:** Користувач обирає локацію (наприклад, *«Піп Іван»*) та клас авто (*«Hard»*). Натискає «Розрахувати ризик та вартість».
2. **ViewModel Pass:** `OrderViewModel` передає вхідні дані в `CalculateRouteSafetyUseCase` та `CalculateTripCostUseCase`.
3. **AI Safety Engine Execution:** `SafetyEngineEvaluator` зіставляє рівень складності маршруту та можливості авто, генерує `SafetyVerdict` (показник ризику, попередження, рекомендацію) та підраховує вартість подорожі.
4. **Data Persistence:** При підтвердженні `SaveOrderUseCase` зберігає створений об'єкт `TripOrder` у локальну базу даних **Room DB**.
5. **UI Update:** `Room DB` емітить оновлений `Flow<List<TripOrder>>`, UI відображає підтвердження та збережену історію.

### 3.5. Межі курсу (Scope / Out of Scope)
* **In Scope (В межах курсу):** Android Native (Kotlin), Jetpack Compose UI, Clean Architecture (Domain/Data/Presentation), Room DB persistence, Локальний AI/Rule-based Safety Engine.
* **Out of Scope (За межами курсу):** Реальний backend-сервер (REST API/GraphQL), інтеграція платіжних систем (LiqPay/Stripe), реальний GPS-трекінг у реальному часі.

## 4. Основні вимоги до застосунку 

### 4.1. Функціональні вимоги (FR)
* **FR-01:** Система повинна надавати можливість вибору локації/маршруту зі списку гірських точок Карпат.
* **FR-02:** Система повинна дозволяти вибір класу авто: *Light, Hard, Extreme, VIP*.
* **FR-03:** Система повинна розраховувати та виводити AI-вердикт ризику (рівень безпеки у %, рекомендації, застереження).
* **FR-04:** Система повинна розраховувати підсумкову вартість подорожі (Базова ставка $\times$ Тривалість).
* **FR-05:** Система повинна зберігати сформоване замовлення у локальну базу даних Room DB.
* **FR-06:** Система повинна відображати список збережених замовлень (історію) користувача.

### 4.2. Нефункціональні вимоги (NFR)
* **Performance:** Час розрахунку AI-вердикту та вартості не повинен перевищувати 300 мс на пристрої.
* **Offline-behaviour:** Застосунок повинен повністю зберігати функціональність розрахунку та створення замовлень без наявності підключення до мережі Інтернет (Offline-first).
* **Security:** Локальні дані замовлень зберігаються у закритому пісочнику (App Internal Storage / Room DB) пристрою.
* **Accessibility:** Підтримка системної темної/світлої теми, розмінність шрифтів згідно з гайдлайнами Material Design 3.

### 4.3. Граничні випадки (Edge Cases)
* **Невідповідність класу авто та маршруту:** Спроба обрати клас *Light* (паркетник) для маршруту *Піп Іван* (складність 9/10) має виводити блокуючий AI-вердикт із високим рівнем ризику (>85%) та рекомендацією змінити клас авто на *Extreme*.
* **Порожня база даних:** При першому запуску додатка екран історії замовлень повинен коректно відображати порожній стан (Empty State) із пропозицією створити перше замовлення.

### 4.4. Acceptance Criteria (Given / When / Then)

#### Сценарій 1: Успішний розрахунок безпеки та зберігання замовлення
* **Given:** Користувач перебуває на головному екрані розрахунку.
* **When:** Користувач обирає локацію «Озеро Несамовите» та клас авто «Extreme», після чого натискає кнопку «Розрахувати».
* **Then:** Система відображає AI-вердикт з високим рівнем безпеки, показує розраховану вартість (20 000 грн) та зберігає замовлення у Room DB.

#### Сценарій 2: Виявлення підвищеного ризику AI-рушієм
* **Given:** Користувач обирає складний маршрут «Піп Іван (Чорногора)».
* **When:** Користувач обирає клас авто «Light» та натискає «Розрахувати».
* **Then:** Система відображає AI-вердикт «Високий ризик / Не рекомендовано», показує деталізоване застереження та пропонує змінити клас авто на «Hard» або «Extreme».

### 4.5. Пріоритетизація MoSCoW (MVP vs Post-MVP)

* **Must Have (MVP):**
    * Форма вибору локації та класу авто (*Light, Hard, Extreme, VIP*).
    * Інтеграція `CalculateRouteSafetyUseCase` та `CalculateTripCostUseCase`.
    * Відображення результату AI-вердикту та вартості.
    * Збереження та зчитування замовлень через Room DB.
* **Should Have (Post-MVP):**
    * Фільтрація та сортування збережених замовлень в історії.
    * Можливість видалення/редагування замовлення з Room DB.
* **Could Have (Post-MVP):**
    * Інтеграція симуляції погодних умов у реальному часі (дощ/сніг/туман) для коригування AI-вердикту.
* **Won't Have (на даному етапі):**
    * Онлайн-оплата замовлень.
    * Реальний GPS-моніторинг водія на карті.
